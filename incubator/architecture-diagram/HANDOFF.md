## Owner direction

- Improve the skill, not one diagram. A good result must come from a fresh session that has only the package and a scenario, not from an agent repairing output with this conversation's context.
- Layout must express meaning, not mathematical tidiness. Runtime path in the middle; build, ingestion, management and telemetry in their own lanes; true boundary nesting. Treat a source's numbered steps as an unordered list while laying out; once the layout is settled, number the steps by the execution order the drawn architecture implies. Readers find the sequence by its numbers, so 1, 3, 2 in space is fine, while tangled lines are not (owner, 2026-11-03, replacing the earlier "numbered steps in reading order"). Avoid detours: a line that leaves and re-enters a region reads as data leaving it. Never delete, merge or move an element out of its region to clear a check.
- Placement follows the user's instructions and intent first, then the vendor's standard practice and platform constraints where the source is silent, named as inference. An obvious conflict between the two is reported before drawing with a recommendation (owner, 2026-11-04). This replaced the rule that kept every service of unstated region outside a stated region, which left an EKS cluster outside its load balancer's region.
- Prefer notation readers already know. Do not use self-invented rules of unclear meaning, such as dots or circles on line ends or boundaries; where a package convention is used, the key must state its meaning (owner, 2026-11-04). Following the [connector encoding research](../../research/diagrams/architecture-diagram/connector-encoding-conventions-2026-11-04.md), the owner adopted: one filled arrowhead, solid and dashed only (no dotted), one line weight (the main path shown by place and step numbers, owner, 2026-11-04), no hue without a second cue, no notation-specific ends unless the key declares the notation, and a key that lists every style once a view has two or more kinds of line (one kind needs no key), drawn as a native draw.io table titled "Key" with a sample line and its meaning per row. Boundaries follow the same standard: vendor boundary styles as the vendor defines them, every other boundary a thin solid neutral outline named by its title.
- Two kinds of line carry a view: solid for the main flow, dashed for supporting flows such as deployment, management, telemetry, secrets and DNS. A third kind of line or end is a last resort: first split the view; if a kind is still added, the key explains it, and split views share one notation across their pages (owner, 2026-11-04).
- An arrowhead points where the request or data moves (owner, 2026-11-05). A call points to the service it calls. A read, pull, poll or sync of a queue, secret store, configuration, repository or registry points from the store to its reader; an arrow into one says the sender writes there. This replaced the rule that an arrow runs from initiator to callee, which made pulls read as the reverse of the real flow and is a correctness error.
- Splitting is recursive: a view answers one question; split it by concern, zoom or flow when it needs a third kind of line, a second direction, deep nesting, a crowded center or a wide page, and test each new page the same way. Split views are pages of one file with the same names, symbols and line meanings, and overview boxes link to their detail pages (owner agreed, 2026-11-04).
- Do not split casually (owner, 2026-11-05). One view is the default; runtime and auxiliary relationships share it as solid and dashed lines. Split only when a laid-out page still breaks a hard limit (a third kind of line, wider than 1400 units, more than three nested outlines, two crossing main directions), into as few pages as fix it.
- Draw an identical repeated structure, such as environments or a warm-standby region with the same stack, once with its count and names; draw copies only where they differ. A page wider than 1400 units is a layout-check error (owner, 2026-11-05).
- Icons must be real upstream artwork that travels with the package, shown at one standard size. Never draw or recolor an icon; use the plain-box fallback when none exists.
- Output must import into Lucidchart as well as open in draw.io.
- Talk to the owner in Chinese; write repository content in English.

## What the package does now

- `find-icon.mjs` looks up the draw.io catalog (AWS, Azure, Google Cloud, Kubernetes) and `assets/vendor-icons.json` (92 platform and AI vendor icons from pinned `@thesvg/icons`, `@fabric-msft/svg-icons` and official repositories, with licence and SHA-256). It returns a standard placement: symbols in a 72 square, wide marks 40 high, captions below at 16 point with `labelWidth` 160, or the plain-box fallback.
- `finalize.mjs` embeds vendor artwork and rewrites the file in draw.io's own layout, one element per line. Lucidchart rejects any other layout of the same XML; this was confirmed by owner import tests on 2026-11-02. `check-layout.mjs` errors and `render.mjs` refuses until the file is finalized.
- `check-layout.mjs` estimates caption, boundary-title and connector-label boxes and connector routes, and reports text collisions, labels away from their line or on a bend, connectors through captions, leaving and re-entering or passing through regions, detours, jogs, crossings, ports to swap, bends that a clear straight or one-bend route would avoid (a simpler route through an element, a caption, an extra region outline or a new crossing counts as blocked), members named like the boundary they sit in, and more than three nested outlines (fills without a stroke do not count). A segment shared by connectors of different meaning, judged by label and line style with unlabelled connectors never matching, is an error; a shared run of identical connectors stays a check. Errors also cover: mixed connector styles without a key table entry for each, dotted lines, more than one weight, ends other than one filled arrowhead that the key does not name, key entries that differ between pages, and custom boundaries with dashed, multi-colour or multi-weight outlines without a key. With several pages, the layout check reports each page by name, and also reports dashed lines too short to show their dashes, page links to missing pages and an element whose symbol changes between pages; `render.mjs` writes one PNG per page. `check-steps.mjs` compares a source's numbered steps (top-level `1.` items or inline `(1)`) with the step numbers on connector label lines. Estimates were calibrated against exact render geometry: every real overlap was found; extra reports were near misses.
- `composition.md` holds the placement and routing rules above; `SKILL.md` says the checks report symptoms and must not be satisfied by changing meaning.
- Authoring tools: `tools/build-vendor-icons.mjs` regenerates the vendor icons and `--check-latest` reports newer upstream versions. Research behind the sources: [vendor icon sources](../../research/diagrams/architecture-diagram/vendor-icon-sources-2026-11-02.md).

## Open problems

1. Tangled steps and needless bends. The rules used to demand that numbered steps read in order, which, with scenarios that list steps 1, 2, 3, likely pushed sessions to place and port by number and tangle lines (round 3 B: `2` and `3` cross). The rules now place by role and lane and order ports to avoid crossings; round 3 A's 1, 3, 2 is acceptable. `check-layout.mjs` also reports bends that a clear straight or one-bend route would avoid, as in round 3 A's `Run`. Whether fresh sessions produce untangled layouts is untested: rerun both scenarios (problem 4).
2. Shared services. Round 3 B still left AI Search to one side, so the ingestion write takes a long route and crosses `3. Store conversation`. The rule exists; consider stronger guidance or an example.
3. Fresh sessions in the Codex sandbox cannot render: `render.mjs` stops with `listen EPERM` (see the [round 1 agent report](./evals/semantic-routing-2026-11-02/round1-a/agent-report.md)), so they never see their image. Static checks partly compensate. A renderer that needs no local listener would close the gap.
4. The [clean-session trials](./evals/clean-session-2026-11-02/README.md) reran both scenarios at `cc7d529` in Claude Code: A 7/10 with numbered, untangled steps; B 6/10 with AI Search placed between its flows but the query calls left unnumbered and unlabeled. After `f8ae813` required stated steps to be numbered and labeled, a rerun of B scored 7/10 with `1 search`, `2 answer` and `3 store` untangled; it still framed every Azure service in `westeurope`, which the source states only for the web app. Its secrets and telemetry lines enclosed the data services like a frame; after `a3c662c` a rerun had none but scored 6/10, because connectors of different meaning shared trunks (Deploy on `1 Ask`, `2 Search` with secrets and telemetry), which the layout check reported and the session kept. After `d8e0d3b` forbade shared segments, the next rerun drew every connector as a straight diagonal (`edgeStyle=none`), which the layout check cannot assess, and still framed every service in the region, following `cloud-conventions.md`. After `c14828a` required orthogonal connectors, stated regions and numbers only for stated steps, a rerun was orthogonal, untangled and numbered 1 to 3 (7/10), but still framed every service in `westeurope`. Scenario A rerun at the baseline package scored 7/10, as before; its main finding is an avoidable crossing of `1 retrieve` with `read`. A [boundary-membership check](./evals/boundary-check-2026-11-03/README.md) on scenarios 01, 03 and 04 found no element drawn into an unstated boundary, so B's over-framing is left as scenario-specific (owner decision, 2026-11-03); scenario 02 was not run. One run each, Claude Code only; Codex was not rerun.
5. Minor issues to watch. The owner accepted the view-splitting results as passing (2026-11-04) and asked to collect more feedback before fixing these. Fix one when later runs show it often or it misleads readers:
   - names drift between pages (both [view-splitting](./evals/view-splitting-2026-11-04/README.md) runs);
   - build and deployment drawn solid, notably on an operations page (scenario C, legend trial A);
   - an overview that links to only one of several detail pages, and does not show which boxes have detail pages;
   - a collinear but non-overlapping pair of lines that reads as one bus (legend trial B).
   - a dashed boundary reads like a dashed connector, and the key lists no boundary style;
   - one key word, "supporting flow", names several unlike dashed relationships;
   - a repeated standby region drawn as a single database reader does not show "same stack" ([wording trial](./evals/wording-2026-11-05/README.md)).
6. Not verified: repeatability across several runs, Claude Code sessions (usage limit hit during this work), offline Desktop use on another machine, and redistribution terms for icons whose licence requires attribution (Jenkins, CC-BY-SA-3.0) or limits use (Microsoft Fabric).

## How to evaluate a change

1. Copy `candidate/architecture-diagram` into `<tmp>/.agents/skills/`, add one scenario as `scenario.md`, run `git init`, and run `codex exec -s workspace-write "Use the architecture-diagram skill to create diagram.drawio from scenario.md. Write your companion account to agent-report.md."` there. Set up the directory before starting the session, not in parallel.
2. Render with `node candidate/architecture-diagram/scripts/render.mjs <diagram.drawio>` outside the sandbox and inspect the PNG.
3. Ask a read-only subagent with no other context to read scenario and image and score fidelity, meaning of layout and misleading geometry.
4. Record the run and review in a new `evals/<topic>-<date>/README.md`. Finish repository changes with `npm run check` and `npm run skill:check`.

Update this handoff by consolidation when the continuation state changes.
