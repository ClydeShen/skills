The image is titled “Dynamic diagram (deployment view): Partner amendment requests through SOAP to AWS validation.” Its stated purpose is to authenticate partner amendment requests, authorize the required user-profile role, validate in AWS, and return XML through the originating SOAP API.

Boundaries and elements

Two large deployment-node boundaries are shown: Azure Cloud and AWS Cloud. Two external software systems, “Existing partner integrators” and “New partner integrators,” sit outside Azure on the left. A “Site-to-site VPN” container, described as an “Azure ↔ AWS connection,” sits in the gap between the two cloud boundaries, outside both drawn boundaries.

Azure contains an “Azure API Management (APIM)” deployment node. This contains three containers: “Legacy SOAP API” (SOAP API), “Partner SOAP API” (SOAP API), and “APIM policy processing” (Azure API Management).

Azure also contains an “Inbound processing” software-system boundary. Inside it are “API-Route-Processor” and “Common-Authx-Handler,” both identified as Logic Apps workflow containers. Inbound processing further contains a nested “Sub-workflows” software-system boundary, enclosing two more Logic Apps workflow containers: “Amend-Order-Processor” and “Amend-Document-Processor.” The route processor and common authorization handler are outside the nested Sub-workflows boundary.

Two other containers are inside Azure but outside the APIM deployment node and Inbound processing boundary: “Azure AD B2C” (Identity provider) and “Roles / permissions” (Azure Cosmos DB).

AWS contains an “API Gateway” container of type AWS API Gateway. AWS also contains a “Core platform” software-system boundary with one “Validation engine” container of type AWS Lambda function. API Gateway is outside Core platform but inside AWS Cloud.

There are two external-system boxes and twelve named containers in total: nine containers in Azure, the VPN between the clouds, and two containers in AWS. Of the nine Azure containers, four are Logic Apps workflows.

Shared processing, authorization, and failure requirements

A note applies to both amendment sub-workflows. They validate XML, method, and malformed base64; wrap decoded XML in JSON; transform the JSON response through a Liquid template into XML; and return XML through the originating SOAP API.

The method-authorization table gives two rows. Method amend_order requires the user-profile role ManageOrders, and its user profile is Mandatory. Method amend_document requires the user-profile role ManageDocuments, and its user profile is also Mandatory. An accompanying note says the APIM system-account role checks and Common-Authx-Handler user-profile role checks are distinct controls.

The failure-handling note says to hide internal errors, with an AWS-call timeout given as an example. Only a generic error response should be returned through the originating SOAP entry. The mapping is Legacy to existing integrators, and Partner to new integrators.

A note inside AWS says the AWS amend operation and response schema are unspecified. It says the validation engine applies business-rule validation.
